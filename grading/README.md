# Local grading

From the repository root, run `make grade` for a row-by-row score out of 100 on this checkout. For a ZIP you prepared, run `make grade GRADE_ARGS="submission.zip --trust-code"`. Add `--json` for machine-readable scores and evidence. The runner uses recorded model responses, deterministic test doubles and the public regression suite. It replays recorded agent actions. Its default report judge makes one grading request per report to the model configured in this repository’s `.env`. Use `--offline` for course-style grading without model calls or remote testbeds. These local checks approximate the unpublished instructor tests.

- **Observation experiment**. Use any two distinct model IDs. Save each pair as `artifacts/part3-{legal-moves,no-legal-moves}-<tag>.json` with a matching `-result.json`. The grader reads the provider model IDs, verifies each observation condition and replays the moves against the recorded board and result. Flash and Pro qualify. Renaming one model's evidence does not give it a second slot.
- **Partial and pending points**. The 19 rows retain the assignment weights. Within each 6-point compaction implementation/trajectory row, the scripted test and the submitted trajectory are worth 3 each. Each verified A/B condition earns 1 point. The local material-reduction check requires net positive reduction across events and at least one 10% drop, using the scaffold's estimator. Missing evidence fails its check. Missing grader dependencies or a pending human assessment appear separately.
- **Reports**. The grader verifies numerical comparisons against trajectory metrics (2 points) and sends the report and metrics to the OpenAI-compatible endpoint in the grader’s `.env` for qualitative scoring (2 points). The same request evaluates the numerical comparison when the deterministic table check cannot verify the format. Scores include reasons and the model ID. Provider errors or invalid responses leave only the unresolved criteria pending. A grader can override a whole report row with `--review review.json`, for example `{"tokens":{"awarded":3,"reason":"Correct totals and trend; missing summary-call overhead."}}`. An optional `--baseline path.json` supplies the full-context trajectory for ZIP evaluation.
- **Patch testbeds**. Chess uses a fresh copy of the pinned submodule commit and the public regression manifest (`--chess-evaluation DIR` selects another). For trusted inputs, Django uses `--django-source /path/to/django` when supplied, otherwise it starts the course’s billable Modal testbed. `--modal-replay` runs both patches on Modal. To reuse a previous result, explicitly select a trusted runner log with `--django-replay-log artifacts/django__django-15368-check.log`. The grader checks the exact embedded patch bytes, image name, test IDs and complete passing summary and labels the score as a previous replay. It never trusts a log in a submission ZIP.
- **Submission boundary**. A ZIP is overlaid on the tracked course starter, not the solution in this checkout. A directory can be graded during development, but only a compliant ZIP receives packaging credit. The current checkout runs locally as trusted code. For other inputs, `--trust-code` enables local implementation tests and patch execution. Use an isolated disposable environment for third-party code. Model-written Python in a skill trajectory is inspected and its observed board transition replayed; the grader does not execute the recorded snippet on the host.
- **Verification**. Run `make test-grader` to test the grader itself. The first invocation may install the chess replay and SOCKS proxy dependencies. After dependencies are installed, `make grade GRADE_ARGS="--offline"` runs without network access.

The [worked scorecard](scorecard.md) explains all 19 rows for the current work. The simulation and sandbox Python rows each award 3 points for the successful path and 3 for failure handling. A saved report review may specify `report_sha256`; changing the report invalidates that review. Keep the scorecard and review files outside the submission ZIP.

For the 2 interpretation points, the token report earns full credit by explaining how the summary cost and subsequent prompt sizes contributed to the observed total. Explaining one side can earn 1 point. The observation report earns full credit by interpreting the change within each of the two model pairs and limiting conclusions to what the games support. Discussing just one model or restating numbers can earn 1 point. Either direction of effect and any game outcome qualify.
